# Owner Decisions

**Document type:** Decision log.

**Scope:** This log records decisions that the owner made. Each entry states the decision, the reason given, and the design section that carries it out. Decisions recorded in another repository, such as relay decision D3 in `relay-driver/docs/decisions.md`, are cited where they are used and are not copied here.

| ID | Date | Decision | Reason | Design |
| --- | --- | --- | --- | --- |
| PS-D1 | 2026-09-24 | The relay backend is a client of an `mcp-vm-relay` server session and uses the official `@modelcontextprotocol/sdk` client. | The owner retired `pi-vm-relay` in favor of `pi-mcp-adapter` with `mcp-vm-relay`. | [Computer use §11.2](arch/computer-use.md#112-relay-client) |
| PS-D2 | 2026-09-26 | An agent definition may set the child's thinking level with an optional `thinking` field. The computer-use definition sets `thinking: off`. | Qwen 3.8 27B has a known thinking problem. Thinking stays off until enough run data exists to fine-tune the model. | [Subagents §5.3](arch/subagents.md), [computer use §4.3](arch/computer-use.md#43-integration-with-the-subagent-subsystem) |
| PS-D3 | 2026-09-26 | The button-name rule is removed. A check before a plan runs rejects only a plan that cannot run. It never rejects a plan on a guess about what the planner meant or about a future screen. | A check before the run understands only part of what the runtime supports. Rejecting everything outside that part rejects correct plans: in the Calculator task, the rule rejected "the display shows 7" three times, and the fallback left three of four steps unverified. | [Computer use §5.2](arch/computer-use.md#52-computer_run_plan) |
| PS-D4 | 2026-09-26 | Plans are built from the controls the observation offers. A step names its control by region, role and name. The runtime confirms the control in a fresh read before acting, and stops a plan whose window changed since the observation it was written against. | The plan is valid when it is built, and the runtime catches what changes afterwards. An independent review on 2026-09-26 found that the planner's output is not constrained by the tool schema, so the runtime check remains necessary. | [Computer use §5.2](arch/computer-use.md#52-computer_run_plan), [§9](arch/computer-use.md#9-step-lifecycle) |
| PS-D5 | 2026-09-26 | The executor receives the window's accessibility content ranked by priority, and the request builder removes the lowest-priority content first when the request is too large. Controls that can be clicked, with their role, full name and state, are never removed. | The names-only table left out the role of TextEdit's text area, and the executor answered "none" to all 9 requests that needed it. With the role, it chose the text area in 20 of 20 tries. A complete tree does not fit the executor's 4,096 tokens for most Finder and TextEdit reads, so content must be ranked. The full model is sent only if it is at least as accurate as priority 1 alone. Measured on 2026-09-26, it was not (199 against 201 correct of 280), so the executor receives priority 1 alone. | [Computer use §6.2 and §7.1](arch/computer-use.md#62-ui-element-table) |
| PS-D6 | 2026-09-26 | The harness assigns a platform to every observed element from its position, such as iOS for elements inside the iOS Simulator's device screen and macOS for all others. The actions offered for a step follow the platform of the step's control, and the planner never writes the platform. | One Simulator window holds two platforms whose elements the accessibility tree reports with the same roles. In the Dark Mode task on 2026-09-26, the executor chose the Simulator's macOS search field for a step on the iOS search field. | [Computer use §6.5](arch/computer-use.md#65-platform-of-each-ui-element) |
| PS-D7 | 2026-09-26 | Every action comes from a closed allowlist for its platform, with a name, a definition and the host input it sends. Before a plan runs, the executor reads each step's intent against the allowlist; when its reading disagrees with the step's fields and its confidence is above the confidence gate, code edits the fields and records the edit, and otherwise the step returns to the planner with the conflict named. | The planner wrote "Press Return" with the action `press`, which our schema defines as a click. All 7 such steps in the 79 recorded steps clicked instead of pressing the key. | [Computer use §5.5](arch/computer-use.md#55-intent-and-field-consistency) and [§7.2](arch/computer-use.md#72-actions) |
| PS-D8 | 2026-09-26 | The computer-use agent knows whether it runs an accessibility test or ordinary work. Only an accessibility test sends accessibility events. Ordinary work always simulates real user input, through cua-driver or Playwright: pointer input in screen coordinates for the menu bar and every other element, synthesized key events, and for browser pages the Chrome DevTools Protocol `Input` events, which the browser treats as trusted user input. Accessibility actions and DOM-level shortcuts such as `element.click()` are not ordinary input. | Owner decision D3 of the relay requires real input for ordinary work. On 2026-09-26, cua-driver 0.12.6 answered a window-pixel click on the iOS Simulator with an accessibility press (`path: "ax"`), and the menu bar is reachable only in screen coordinates. | [Computer use §11.4](arch/computer-use.md#114-input-mode) |
| PS-D9 | 2026-09-26 | Computer-use work is driven by evaluation. A small fixed task set decides whether the agent ships, and a public macOS benchmark measures its success rate against other agents. What to build next is chosen by the failures these evaluations count, not by discussing each use case in advance. | Deciding use case by use case whether something is necessary took hours of discussion. A measured success rate on shared tasks answers that question and compares the agent with others. | [Computer use evaluation](testing/computer-use-evaluation.md) |
| PS-D10 | 2026-09-27 | Lifecycle failures in the relay stack are fixed reproducer first. Each failure in the relay VM troubleshooting report gets an automated reproducer in the repository that owns the faulty code (pi-secretary, mcp-vm-relay, vm-service or relay-driver). The reproducer is committed failing, and then the fix makes it pass. Reproducers use fakes and scripted servers, never a real VM. Fixes stay on a branch in each repository until the owner reviews them; nothing is pushed or published. A fix that would change a documented behavior of another project, such as keeping the VM after a failed finish or the 6 h grace period, gets a reproducer only, and the behavior change waits for the owner's decision. | On 2026-09-26, VMs were held for up to 20.7 h after their runs ended, and the causes spanned four repositories. A reproducer proves the cause, shows that the fix works, and stops the failure from coming back. | `.troubleshooting/2026-09-27-01-42-17Z-relay-vm-leaks.md` (not versioned) |
| PS-D11 | 2026-09-27 | The computer-use subagent owns the relay machine's lifecycle. It acquires the machine, and it finishes or releases it before its run ends, including when the run is cancelled or Pi shuts down. All computer-use work is delegated to the subagent, and Pi's main agent is not given the relay tools. | The agent that acquires the machine keeps its lifecycle balanced. A main agent with the relay tools would need a last chance to release its machine when it ends, which the owner considers a poor design. | [Computer use §11.2](arch/computer-use.md#112-relay-client) |
| PS-D12 | 2026-09-27 | Relay evidence has no size limit. Screenshots are not scaled, compressed or budgeted, and the relay's 512 MiB and 10,000-file bound on delivering its evidence is removed. | The owner never designed a limit; it was introduced while the relay was built, and it made finishes fail (troubleshooting §10.5). | `mcp-vm-relay/docs/lifecycle-fixes.md` (R8), `relay-driver/docs/decisions.md` (D4) |
| PS-D13 | 2026-09-29 | Destructive actions follow a permission mode set in configuration, as Claude Code's permission modes do: `ask`, `auto` or `bypass`, with `auto` the default. In `auto`, code decides from the action's effect and the environment: an effect that stays inside an ephemeral relay machine proceeds and is recorded, and an effect that leaves the machine, or destroys something in a persistent environment, needs a person's approval. The planner and the parent agent never authorize a destructive action. | Asking a person for every destructive step waters approvals down; in an ephemeral machine, a destroyed file or note is gone with the machine anyway. The live ACC-CU-04 run showed the planner authorizing a deletion itself (verification report of 2026-09-27). | [Computer use §8](arch/computer-use.md#8-decision-policy) |
| PS-D14 | 2026-09-29 | Before the executor service (Jev) is linked as the permission guardian that classifies an action's effect in `auto` mode, it is evaluated with the deterministic request format that production will send. Jev is used as the guardian only if that evaluation passes. | The owner wants evidence that Jev recognizes dangerous actions before relying on it. | [Computer use §8.4](arch/computer-use.md#84-guardian-request), [evaluation §8](testing/computer-use-evaluation.md#8-permission-guardian-evaluation) |
| PS-D15 | 2026-09-29 | The permission modes and the guardian are built and shipped now, although the guardian failed the proposed pass criteria (PS-D14). What improves next is decided from failures collected in real runs and evaluations, not from further discussion or offline evaluation. Settings the owner has no answer for, such as the pass criteria and whether `bypass` is allowed outside an ephemeral machine, are chosen provisionally and marked so in the design. Every permission judgment, and every answer a person gives, is recorded so that runs produce failure cases. This supersedes the condition of PS-D14 that Jev is used only if the evaluation passes. | Without tests, user feedback or real runs, no one can say which mode or guardian is better; waiting for an answer stalls the project indefinitely. | [Computer use §8.5, §8.6 and §12.1](arch/computer-use.md#85-approval-by-a-person) |
| PS-D16 | 2026-09-29 | Adding an item to a cart and saving it for later do not leave the machine by default. The user can change this with their prompt. | The owner's ruling on the two disputed labels of the guardian evaluation. | [Computer use §8.4](arch/computer-use.md#84-guardian-request) |
| PS-D17 | 2026-09-30 | The computer-use agent comes with its own trajectory viewer, which runs outside the relay machine. For each computer-use agent it shows the prompt that spawned the agent, the agent's messages and tool calls, and, between them, the steps each call ran in the machine. | The relay's viewer runs on the machine's evidence and shows only the steps in the machine. Reviewing the first failed evaluation run, the owner could not see the spawning prompt, the agent's messages, or what it did before its first observation. The review runs outside the machine, where the agent's session is available. | [CU-08](user-stories/computer-use.md#cu-08-review-what-the-agent-was-asked-said-and-did), [UX](ux/computer-use.md#1-trajectory-viewer), [computer use §12.3](arch/computer-use.md#123-trajectory-viewer) |
| PS-D18 | 2026-09-30 | The trajectory viewer of PS-D17 is the relay's review app, moved from the relay stack into the computer-use extension. The moved app joins the computer-use agent's messages into what it presents, between the steps that ran in the machine. The relay stack drops the viewer app. | Without the agent's messages, the relay's viewer waters the review down, and only the computer-use extension has both the agent's session and the machine's evidence. A separate page next to the relay's app was not what the owner asked for. | [UX](ux/computer-use.md#1-trajectory-viewer), [computer use §12.3](arch/computer-use.md#123-trajectory-viewer) |
| PS-D19 | 2026-09-30 | The planner never writes the check of a step, and the executor only executes. The planner learns the result of what the executor did, and that result is the check. No check runs before a step: a step is never skipped or stopped because a condition already holds. | Correctness comes before performance. A postcondition is a string and tree predicate that code matches, with no visual understanding, so it cannot judge what only a capable model looking at the screen can. Run before the step, it cut the branch: in the Reminders run of 2026-09-29, "text contains Reminders" held on the welcome window, and the plan stopped without clicking Continue. | [CU-02, CU-03, CU-05](user-stories/computer-use.md#cu-02-know-what-happened), [computer use §5.3, §5.4](arch/computer-use.md#53-who-judges-a-step) and [§9](arch/computer-use.md#9-step-lifecycle) |
| PS-D20 | 2026-09-30 | The planner always issues its next plan from the previous execution result. Judging that result and writing the next plan are one step: the window after a plan is the next plan's `based_on`, and the planner reads the window again only for its first plan or when the result carries no window. | Understanding the execution result is the planner's responsibility, and the result already shows the window after the plan. A separate observation between plans repeats that read and splits the judgment from the planning it feeds. | [computer use §5.3, §5.4](arch/computer-use.md#53-who-judges-a-step) |
| PS-D21 | 2026-09-30 | A plan has no action budget. The `maxActionsPerPlan` setting and the `budget_exhausted` escalation are removed. | Each step acts once and a plan has at most 50 steps, so a plan sends at most 50 actions and never reached the budget of 100. The budget guarded against repeated actions, which PS-D19 removed. | [computer use §9](arch/computer-use.md#9-step-lifecycle) |
| PS-D22 | 2026-09-30 | The thing a step acts on is a UI element, not a control. The term is "UI element", not "control" or "element": the step field `control` is renamed `ui_element`, and the control check is the UI element check. | "Control" means a control in the sense of `NSControl`. | [computer use §5.2](arch/computer-use.md#52-computer_run_plan) |
| PS-D23 | 2026-09-30 | The computer-use parts are the planner, the executor and the grounder. The executor is `computer_run_plan` with its step loop: it reads the window with `get_window_state`, runs the checks, asks the grounder and the permission guardian, and sends the input. The grounder is the jev structured-decision service, `/v1/systemone`, which picks the UI element and the action for each step from the executor's latest read; it was called the executor before. The harness is no longer a separate part. | The executor is what executes the plan, so the code that issues `get_window_state` and the input is the executor. | [computer use §1](arch/computer-use.md#1-purpose-and-scope), [§4.1](arch/computer-use.md#41-responsibilities) |
| PS-D24 | 2026-09-30 | The executor does not check a step's named UI element against the window. The UI element check and the cross-check of the grounder's choice are removed. The step's `ui_element` goes to the grounder with the step, and the grounder chooses the UI element. | The cross-check repeats the failure of the removed pre-check: code compares a name the planner copied from one read with a later read, and a name that changes, such as a text area named by its content, stops a correct step. | [computer use §9](arch/computer-use.md#9-step-lifecycle) |
