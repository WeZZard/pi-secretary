# Test Artifact Policy

**Scope:** This policy separates versioned test inputs and specifications from generated run output. It applies to local development, acceptance testing, and CI.

## 1. Principle

**Commit what is needed to reproduce and evaluate a test. Store individual execution results as artifacts, not as source documentation.**

This is a common engineering practice rather than a universal directory-name standard. GitHub documents workflow artifacts for retaining test output, and Playwright's CI guidance uploads generated reports as artifacts. Intentional expected snapshot baselines are a different category and can be versioned after review.

| Category | Location | Version-control treatment |
| --- | --- | --- |
| Test implementations and deterministic fixture inputs. | They live under `tests/` and supporting source directories. | They are committed and reviewed. |
| Acceptance specifications and reproduction instructions. | They live under `doc/acceptance/` and `docs/`. | They are committed and reviewed. |
| Intentional expected snapshot baselines. | They live in a clearly identified fixture or baseline directory under `tests/`. | They can be committed after an explicit review of the expected behavior. |
| Logs, actual-result captures, recordings, generated reports, and derived screen views. | They live under `test-results/<suite>/<run-id>/` locally. | They are ignored by Git and may be uploaded as CI artifacts. |
| Long-lived conclusions and verification limits. | They live in a concise source document with reproduction instructions and artifact identifiers. | They are committed without embedding a complete archive of each attempt. |

A file extension does not determine its category. For example, an intentionally reviewed expected JSON fixture can be committed, while a generated JSON result report should remain an artifact. Do not add broad ignore rules for all JSON, HTML, or image files.

## 2. Local Directory Convention

```text
doc/acceptance/                 # Versioned Gherkin and acceptance instructions.
docs/testing/                  # Versioned testing policies.
tests/                         # Versioned tests and intentional fixtures.
scripts/                       # Versioned recorders and validators.
test-results/                  # Ignored generated output.
  tui/
    <UTC timestamp>-<id>/
      run-metadata.json
      walkthrough.cast
      checkpoints.json
      result.json
      screen-assertions.json   # Generated by replay.
      screens/                 # Generated on demand by replay.
```

- Run directories identify one execution. A recorder must not overwrite or append to a previous run's output.
- The TUI recorder defaults to a new directory under `test-results/tui/` and prints the resulting path.
- `--output` can select another new or empty directory under `test-results/`, or an explicit external directory such as a temporary artifact location.
- Both recording and replay reject output locations elsewhere inside the repository, including paths that resolve into documentation through a symlink.
- Recorder metadata identifies the source revision and whether the working tree was dirty. A dirty-tree flag is not a reproducible commit identifier by itself; retain the associated patch or CI checkout when reproduction requires it.
- Replay views are derived from the recording. Generate them when needed rather than treating each representation as independent evidence.

## 3. TUI Commands

```bash
# Record an isolated run in a new test-results/tui/<run-id>/ directory.
npm run record:tui

# Replay the path printed by the recorder.
npm run render:tui -- test-results/tui/<run-id>

# An explicit external output directory is also supported.
npm run record:tui -- --output /tmp/secretary-tui-unique-run
npm run render:tui -- /tmp/secretary-tui-unique-run
```

- The recorder runs real pi in a pseudo-terminal using a deterministic local provider and isolated configuration.
- The renderer reconstructs terminal character grids. It does not produce desktop pixel screenshots or establish human visual approval.
- See the [TUI acceptance procedure](../../doc/acceptance/tui-recording.md) for the interaction coverage and verification limits.

## 4. CI Storage and Retention

- Keep generated artifacts outside the Git history. Use the CI platform's artifact service to retain selected test output after its runner exits.
- Upload relevant diagnostics even when a test fails, unless the job was cancelled before evidence could be collected safely.
- Give artifacts names that identify the suite and CI run. Set an explicit retention period rather than accumulating reports indefinitely.
- The project recommends 14 days for routine CI test artifacts. This is a project policy choice, not a limit or default imposed by GitHub.
- Preserve evidence for an unresolved defect or release review in an approved durable artifact store before its retention period expires.
- Review artifact contents before uploading. Environment files, credentials, private prompts, and unrelated user data do not belong in test reports.

For a future GitHub Actions job that already runs the tests, an artifact-upload step can use this pattern:

```yaml
- name: Upload test artifacts
  if: ${{ !cancelled() }}
  uses: actions/upload-artifact@v4
  with:
    name: test-results-${{ github.run_id }}-${{ github.run_attempt }}
    path: test-results/
    if-no-files-found: warn
    retention-days: 14
```

This example is guidance, not a claim that the project currently has this CI job configured. It does not initiate an upload or publish local evidence.

## 5. Cleanup and Existing Evidence

- Local outputs are disposable after the required debugging or review is complete. Remove only explicitly selected run directories whose evidence is no longer needed.
- Recorders do not automatically purge old runs. This avoids deleting the only evidence of an unresolved failure.
- Existing acceptance recordings were relocated to `test-results/tui/legacy-evidence/` without deleting their contents. A generated migration manifest records file hashes so preservation can be checked locally.
- The earlier `attempt-*` directories remain local diagnostic artifacts. They are not additional acceptance requirements and should not be committed.
- Documentation uses reproduction instructions and artifact identifiers instead of Markdown links to ignored local result files. A clean clone should not contain broken links to somebody else's local run.

## 6. Review Checklist

- Confirm that the output directory is ignored with `git check-ignore`.
- Confirm that `git status` contains only intended source, fixture, specification, and documentation changes.
- Confirm that a retained baseline is an expected input to a test, not an unreviewed actual result.
- Confirm that a report distinguishes test execution, capture completeness, and human approval.
- Confirm that shared artifacts have an explicit retention policy and contain no unexpected sensitive data.
